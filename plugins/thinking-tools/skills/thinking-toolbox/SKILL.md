# Thinking toolbox

Adam Jones's 38 thinking tools are routines, not concepts: steps to run in a specific situation. The user wants two things: (1) notice when one fits and say so, (2) walk them through it when they say yes.

Source: https://adamjones.me/blog/thinking-tools-to-be-more-effective-at-anything/ (each tool links to a full article; fetch it if you need more than what's here).

## Flagging

Flag when a tool clearly fits what the user is doing and they aren't already doing it. The point is to build their reflex, so always use Adam's name for the tool, in bold on first mention.

- Respond to what they said first. Put the flag at the end, as one line: `Thinking tool: **<name>** (<why it fits, under 12 words>). Want to run it?`
- If the tool *is* the answer (e.g. "should I research X before deciding?" is Ask if the answer changes the decision; "should we hire more ushers?" when ushers aren't the bottleneck is Optimise only the constraint), apply it directly: compress to the two or three steps that decide the question, give the verdict, name the tool. Don't add "Want to run it?" when nothing is left to run.
- When several tools fit, pick the one that addresses the pain they named. If still tied, pick the one with the cheapest first step.
- Offer at most one tool per reply. Naming a second tool you used in passing is fine ("booking a trial session is Run the experiment"), since naming builds the vocabulary.
- Don't flag on quick factual questions, routine coding or debugging, casual chat, or when they're mid-task and just need the answer.
- Don't re-flag a tool they passed on in the same conversation. If they wave off a few in a row, stop flagging for that conversation.
- Respect each tool's pitfalls. No Grind for someone short on sleep; no Run the experiment when the trial is expensive or risky.

## Guiding

When they say yes:

1. One sentence on what the tool is for and how many steps it has.
2. One step per message. Ask the step's question and wait. They do the thinking; that's how the reflex forms. If they've already done a step, skip it. If their answer is too vague to carry the later steps, sharpen it first.
3. Prompts that belong to the step (like Framestorming's list of angles) are fine to give up front. Your own candidate answers come after their attempt: more options in a divergent step, a challenge in a converging step, numbers in an estimate. If they're stuck, give one prompt to unstick them.
4. Keep messages short. They're often on a phone.
5. End with the result, one concrete next action, and the next tool to chain if one fits.
6. If the tool turns out a poor fit partway, say so and switch or stop.

Related skills: `thinking-tools:premortem` stress-tests a chosen plan (fits PIOSEE's Select step). `thinking-tools:board` gives hard adversarial critique (fits Adopt a scout mindset and Be disagreeable).

## The tools

### Choosing what to work on

**Backchaining**
1. State the goal concretely.
2. Ask what must be true just before it's reached.
3. Ask what must be true before that. Repeat.
4. Stop at something doable today, and do it.
Watch: check the goal is worth chasing first (Musk's 5 steps, Framestorming). Forward chaining still wins for creating luck.
Example: paying users, which needs a prototype, which needs a co-founder, which starts with one scary email today.

**Create surface area for luck**
1. Ask what they care about beyond themselves. Drop "should".
2. Pick a starter: write publicly about a curiosity, start a project, or join a group with a goal and help it.
3. Take one step today.
4. Publish the work so opportunities come inbound.
5. Position for where trends are heading.
6. Apply where rejection is likely; move fast when a window opens.
Watch: count attempts, not hit rate. Unrealistic with no spare time or energy.

**Optimise only the constraint**
1. Name the outcome. Find where work piles up.
2. Exploit: free changes that raise the bottleneck's throughput.
3. Subordinate: pace everything else to it, even if parts sit idle.
4. Elevate: spend to add capacity there.
5. Re-check. The constraint moves.
Watch: speeding up non-bottlenecks only adds work in progress.
Example: the Review column on a Kanban board is full, so help review rather than start new builds.

**Framestorming**
1. Name the problem area.
2. Write several framings as "How do we...?", varying the angle: prevent, detect, cope, different groups.
3. Brainstorm solutions for each framing (run Diverge, then converge here if the list is thin).
4. Check which framing current solutions actually serve. Converge on the strongest.
Watch: framings built inside current assumptions. Talking to users breaks them open.

**Diverge, then converge**
1. Diverge: generate many ideas with criticism banned. Wild ideas and "reward hacks" welcome.
2. Write every idea in one shared place.
3. Only once generation is done, converge: cut hard and pick the gems.
Watch: flipping between modes does both badly. Cutting from many ambitious ideas beats growing a thin list.

**Musk's 5-step design process** (order matters)
1. Make requirements less dumb. Each needs a named person who can say why it exists.
2. Delete parts and steps. If you never add some back, you didn't delete enough.
3. Simplify or optimise what survived.
4. Accelerate: shorter cycles.
5. Automate, last.
Watch: running it backwards, automating what should have been deleted. Keep deliberate redundancy on important bets.

**Choose simple over easy**
1. Simplify the requirements first.
2. For each option, list the concerns it touches and how interwoven they are.
3. Look for fake modularity: a clean interface over entangled parts.
4. Prefer small interfaces, no shared mutable state, few interacting config options.
5. Accept duplication over a DRY abstraction that tangles concerns.
6. If simple and easy conflict, pick simple. If both are simple, take the easy one.
Example: copy two small functions rather than build one heavily parameterised helper.

**Accept redundancy**
1. Is coordinating (gathering context, convincing people) slower than just doing it?
2. Is the work cheap to do?
3. Is the outcome important and uncertain?
4. If yes, take several independent shots, diversified so they don't fail together.
5. Trim with Musk's step 2: keep redundancy only where it earns its place.
Example: Operation Warp Speed backed three vaccine platforms at once.

**Hunt for 100x opportunities**
1. Generate options far more ambitiously: what would they do with 10x, then 100x, their current reach?
2. Get more options from friends and advisors, real or imagined.
3. Compare with made-up numbers. Measure the inputs that matter most.
4. Name value conflicts (impact, life, enjoyment) as trade-offs and accept them.
5. Remember most choices can be undone.
6. If it's still a toss-up, stop stressing.
Watch: deliberating only in their head.

**Pick up the trillion-dollar bill**
1. Name the apparent opportunity concretely.
2. Ask "why hasn't anyone done this?"
3. Look for past attempts and why they failed.
4. Ask whether it's unglamorous schlep others avoid.
5. If no good reason remains, run the cheapest test of whether it's real.
6. Compare against alternatives.
Watch: skipping step 3. Headline numbers that mislead.

**Find problems, not applications for solutions**
1. Name the most important problem for the people involved.
2. Hold the problem fixed. Treat the solution as the variable.
3. Test many solutions by any means, even ones that sideline their favourite tool.
4. Talk to users about the problem, not the idea.
5. When a custom fix recurs, make it the standard.
Example: a proposed weekly sync. Name the problem it fixes and design the smallest fix, or skip it.

**Use leverage against weakness**
1. Name their leverage: a distinct strength, or a reframe of what matters.
2. Name the opponent's or problem's weakness, especially what they traded away to be strong.
3. Check for bottlenecks.
4. Pick moves where their strength costs the other side far more to counter.
5. Lengthen the horizon.
Watch: polishing their own weaknesses beyond major risks; fighting on the other side's terms.
Example: David turns down Saul's armour and takes a sling.

**Be Pareto-best in the world**
1. Name the problems they want to work on. Backchain to the skills needed.
2. List their skills across several dimensions, average ones included.
3. Find an intersection others value whose parts work together.
4. Check elbow room (how much of that space they can claim) and density (how many useful problems live there).
5. If crowded, add a dimension.
Watch: combinations nobody needs, like dentistry plus maritime law.

**Ask if the answer changes the decision**
1. Name the decision.
2. List plausible answers to the open question.
3. Would the decision differ under any of them? If not, stop.
4. If yes, research only the part that moves the decision.
Example: an hour on "is a thermostat an AI system?" changes nothing.

**Defend slack**
1. Name the resource: time, money, people, goodwill.
2. Estimate how much is already committed.
3. Aim for roughly 75-85%, lower where load is unpredictable.
4. Above that, cut commitments or add capacity.
5. Put most slack at the bottleneck.
6. Pad estimates for the planning fallacy.
Watch: slack isn't coasting. Hard work is fine while capacity exceeds load.

**Be a new homunculus**
1. Imagine a newcomer takes over the controls (of them, or of their org).
2. The newcomer owes nothing to sunk costs, guilt or old commitments.
3. Judge only on current merits: what would the newcomer do?
4. Re-check every "I can't".
5. Do that.
Watch: real obligations to other people still count.
Example: Grove asked Moore what a new CEO would do; "get us out of memories". So they did.

### Figuring out what's true

**Adopt a scout mindset**
1. Notice soldier mode: hoping for an answer, relief at confirming evidence, irritation at objections, avoiding a lookup.
2. Make the belief concrete: what would count against it?
3. Write the strongest case for rival views.
4. Find the cruxes and seek evidence that could flip them: the smartest dissenter, or ask Claude for the best counter-case.
5. Hold it loosely: "I think", "I don't know yet".
Watch: turning into endless hedging when a quick check would settle it.

**Be sceptical**
1. Trace the claim to its origin and assumptions.
2. Ask for the denominator.
3. Check causal direction and confounders.
4. Check subgroups; aggregates can reverse.
5. Would the metric move even if nothing changed?
6. What does the framing leave out, and where is it steering?
7. Believe it only as much as the evidence supports.
Watch: cynicism. Demanding trials for everyday choices.

**Suspect mess or misalignment, not malice**
1. Restate what the decision-makers were actually asked to decide.
2. Check whether the outcome is defensible on that narrower question.
3. Look for knock-on effects and constraints.
4. Ask who could change it and whether their incentives point that way.
5. Explain through complexity and incentives before motive.
Watch: concrete evidence of bad faith overrides this. Explaining isn't excusing.

**Make decisions with made-up statistics**
1. Check the answer would change the decision.
2. Break the quantity into a few guessable factors.
3. Multiply through, with units, for each option.
4. Sanity-check each input; halve or double for known effects.
5. Close results are a wash. 10-100x apart, act.
6. Measure the inputs that drive the result.
Watch: present numbers as estimates. If a cheap measurement exists, measure instead.

**Run the experiment**
1. Name the question being argued.
2. Can it be looked up, asked of someone, or tried cheaply?
3. Compare trial cost with the cost of more debate.
4. Run the smallest trial.
5. Compare the result with the prediction and update.
Watch: costly or risky trials (use made-up statistics). Experiments run to win rather than learn.

**Become a narrow expert**
1. Narrow to the specific question, not the field.
2. Map it with precise AI questions and follow-ups.
3. Restate in their own words; chase confusions.
4. Ask why their understanding might be wrong; ask for practice questions.
5. Ask for analogies from a field they know.
6. Defer to real experts within their domain.
Watch: nodding along to plausible text they haven't processed.

**Be disagreeable**
1. Write the belief in its rawest form.
2. Make it falsifiable.
3. Put probabilities on outcomes.
4. Share it with reasoning, numbers, sources, and where they're least sure.
5. Update in proportion to the quality of the pushback.
6. Turn it into a test.
Watch: letting an LLM write the opinion, which dulls it. Use AI to critique only.
Example: "customers don't get us" becomes "they don't know what their current tool costs them"; add a cost calculator and watch conversion.

**Climb the user-contact ladder**
Rungs, best first: be a user; talk to users (their life, past behaviour, what they've tried, no pitching); role-play a user step by step; imagine what they want; ignore them.
1. Name the users.
2. Find the highest rung reachable now.
3. Do it.
4. Act on what they learn quickly.

**Refuse the idiot plot**
1. Name the obvious thing nobody is saying.
2. Check it isn't a raw moment, like grief, where bluntness hurts.
3. Say it as a check: "Just to check we're on the same page, my understanding is..."
4. Invite correction.
5. Earlier silence doesn't bind them.

**Overcommunicate**
1. Name the one thing that must land.
2. Say it in a meeting.
3. Repeat it in another setting.
4. Restate it in another channel: Slack, a 1:1, a status doc.
5. Use each repeat to check people are on track.
Watch: evidence supports 3-4 exposures, not a "rule of 7". Skip for trivia.

### Executing

**Shorten cycle times, reduce batch sizes**
1. Frame the work as build, measure, learn.
2. Shrink to the smallest version a few users can use, even if done by hand.
3. Shorten each loop; run many small experiments.
4. Limit work in progress.
5. Scale only once what to make, and how much, are clear.
Watch: costs throughput and coordination. Skip for predictable repeat work.
Example: the Wright brothers' many short glider tests beat Langley's one big machine.

**PIOSEE** (crises, incidents, important projects)
1. Problem: what exactly is it? (Framestorming, talk to users.)
2. Information: what context matters? (Scout mindset, narrow expert.)
3. Options: list them all, deliberately widening. (Obvious things, backchaining, 100x, diverge then converge.)
4. Select: set criteria, then choose. (`thinking-tools:premortem` here.)
5. Execute. (Grind if needed.)
6. Evaluate: how did it go, what did we learn? Loop to 1.
Watch: Options is the step people skimp. Scale depth to the stakes; it can run in a minute.

**More dakka**
1. Name the lever and the outcome it moves.
2. Would more plausibly keep helping?
3. Is turning it up safe and reversible?
4. Raise it a lot, not a nudge.
5. Watch quality and other trade-offs.
6. Keep going while gains hold.

**Overcorrect, then settle**
1. Change the behaviour well past the target.
2. Watch the result; the overshoot gives a clear signal.
3. Use it to find the middle.
4. Settle there over short cycles.
Watch: staying at the overshoot. Timid nudges that teach nothing.

**Sometimes you just have to grind**
1. Confirm working-smarter options are used up.
2. Is output limited by hours?
3. Is the work meaningful and enjoyable to them?
4. What would extra hours cost: people, rest, other values?
5. Check physical limits: sleep, strain.
6. Time-box a test: a week or two of longer days, tracking sleep and enjoyment.
Watch: don't suggest it when sleep or health is already strained.

**Do the obvious things**
1. Stop before acting on the first idea.
2. List what a reasonable person would do.
3. Ask "what would I tell a friend in this position?"
4. Get obvious advice from people or AI.
5. Do those things.
6. In social settings, ask the obvious question aloud.

**Meet with advisors in your head**
1. Pick two to four advisors they respect, living or dead.
2. Imagine each one's advice on the problem.
3. Note where they disagree.
4. Before a meeting, predict the other person's advice and follow-up questions, and prepare.
5. Decide for themselves.
Watch: it's their guess at the advisor's view, not the view.

### Compounding

**Build feedback loops**
1. Define the loop: build, measure, learn; or spec, run, evaluate, revise.
2. Agree a signal they trust.
3. Run and evaluate against it.
4. Sort gaps: ambiguity means fix the spec; discrepancy means fix the implementation.
5. Shorten the loop.
6. Bake it in so it runs without willpower.
Watch: an untrustworthy signal steers them wrong.

**Be AI-legible**
1. Map where their work lives.
2. Connect each source.
3. Auto-transcribe meetings.
4. Keep notes digital and searchable.
5. Photograph whiteboards into an indexed place.
6. Write a top-level prompt saying what lives where.
Watch: decide what's too sensitive to expose.

**Build systems, not willpower**
1. Clarify the real goal and whether a better route exists.
2. Picture future-them: what will derail them?
3. Raise the value of success: track what they actually care about.
4. Raise the cost of failure: a partner, a fixed time. Not guilt.
5. Make it easy: pre-pack, attach to an existing routine, add a visible cue.
6. Add a feedback loop to tune the system.
Watch: don't let "no system yet" stop them doing it once today.

**Recursively self-improve**
1. Run a retro on recent work.
2. Run a meta-retro: is the improvement process itself working?
3. Check the feedback actually flows.
4. Overcorrect, then settle on changes.
5. Shorten the cycle.

**Think in public**
1. Name what they've done or figured out.
2. Write it up somewhere findable.
3. Make concrete claims a critic could correct.
4. Don't wait to be an expert; capture it while fresh.
5. Keep adding, so it becomes a portfolio.
Watch: confidential work. Vague posts get no useful critique.
